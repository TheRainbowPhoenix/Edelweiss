# XD-A8500 ROM32A mapping contract (reverse-engineered)

Source: user-supplied `ROM32A.BIN` (32 MiB), SHA-256
`224df7b13ea27666f8ea5d24ab3a096784fddd0ab57961c61cce2b3e445cb7fc`
and accompanying Ghidra `ROM32A.BIN.c`.

The image matches all three `XD-A8500 ROM32A` firmware fingerprints in
`exword/firmware.c` at `0x8004634c`, `0x802d89bc`, `0x80025514`.
**Do not redistribute the uploaded ROM**; this document records observations.

## What the firmware actually maps

The reverse-engineered `MMU_HandleTranslationFault` implements:

- **VA below 0x70000000:** fallback physical
  `0x10000000 | (VA & 0x007ff000)` (observed C: `PTEH & 0x7ff000 | 0x10000000`),
  with PTEL flags `0x6c | 0x110`. Therefore an EDL at
  `VA 0x00300000` is **not** backed by malloc's SDRAM:
  the ROM miss handler sends it to `PA 0x10300000`.
- **0x70000000..0x73ffffff:** add-in *primary* mapping, only if
  `ADDIN_PRIMARY_VIRTUAL_START <= VA < ADDIN_PRIMARY_VIRTUAL_END`.
  Physical backing is `ADDIN_PRIMARY_PHYSICAL_BASE` plus the offset.
  The ROM uses flags `0x4c | 0x110`.
- **0x74000000..0x77ffffff:** add-in *API/data* mapping, only in the
  configured API window, using `ADDIN_API_PHYSICAL_BASE`. Flags
  `0x6c | 0x110`.
- Other faults call `MMU_HaltOnTLBError` (terminal error path).

`MMU_ConfigureAddinMappings` initializes primary start from header
offset `+0x2c` (default `0x70000000`) and API start from
`+0x30` (default `0x74000000`); it programs global base/end fields
and **flushes the TLB**. `MMU_ClearAddinMappings` also flushes.

`MMU_InitializeAddinAddressSpace` disables/invalidates TLB, installs
exception handlers, resets add-in mapping metadata and enables translation.
`MMU_EnableAddressTranslation` writes `MMUCR = 0x101`. TLB entries
are loaded with `MMU_InstallTLBEntry` (PTEH, PTEL, LDTLB), using 4 KiB
translation granularity in the observed firmware fault path.

This explains why just installing sixteen 64 KiB UTLB entries does not
provide permanent mappings: they can be replaced and the original firmware
refill would recover the *host's configured add-in backing*, not our
allocator's unrelated pages. gint's world transitions add another owner.

## Dispatcher evidence and allocator gap

The ROM's runtime dispatcher at `0x80024850` reads the runtime function
table address `0x801386c4`. The system dispatcher at `0x800248b0`
reads `0x8018606c`. These addresses were verified against the supplied
big-endian ROM bytes, not guessed from the decompiler labels.

The examined standard runtime table handles OS runtime/input state; the
supplied decomp does **not** identify a public host `malloc/free` pair
or its calling convention. `libdataplus-ex` supplies its own local
`sbrk` allocator and therefore does not prove a native heap syscall.

A future adapter needs **both** an identified and tested native allocation
and release API **and** a way to register or take ownership of a virtual
window in the firmware miss handler, preserve it across gint world switches,
and verify teardown including ITLB aliases. Until then, `acquire_window`
must reject native execution. This is a ROM-specific architectural
observation, not evidence that any-device execution is complete.
